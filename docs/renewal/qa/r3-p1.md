## 1. 점검 장비 (`tools/qa/`)

| 파일 | 하는 일 |
|---|---|
| `scenes.mjs` | 장면 정의(`SCENES` 배열)·캡처·몽타주. 개발 서버가 없으면 띄우고 끝나면 끈다 |
| `saves.ts` | 제품 엔진(`createRun`·`applyCommand`·`advanceTick`)으로 장면 저장본을 만든다(`BUILDERS`) |
| `lib.mjs` | 서버·저장본 주입·이어하기 진입·가짜 시계·DOM 객관 검사 |
| `perf.mjs` | CDP `Emulation.setCPUThrottlingRate` 저사양 측정(§3) |

```
node tools/qa/scenes.mjs --out <폴더> [--scenes 02,05a] [--sizes desk,cb,phone] [--port 5341] [--no-montage] [--list]
node tools/qa/perf.mjs --out <결과.json> [--target dev|prod] [--rates 4,6] [--ambient on,off] [--secs 10] [--reps 3] [--save fx-window]
```

- **진입 방식**: 엔진이 만든 `RunState`를 IndexedDB `vocabulary-td`의 `run` 슬롯에 해시와 함께 넣고(저장 형식은 `src/persistence/db.ts`), 홈의 "이어하기"→"계속하기"로 들어간다. 장면마다 새 브라우저 컨텍스트를 쓴다.
- **연출 시점**: Playwright 가짜 시계로 게임 시간을 직접 흘린다(`계속하기` 뒤 `runMs`). 폭발·장판처럼 순간 연출은 저장본 쪽에서 "연출이 가장 많은 틱"을 엔진으로 찾아 그 몇 틱 앞에서 멈춘 상태로 준다. 같은 장면을 두 번 찍으면 픽셀 0.3% 이하만 다르다. 빛기둥 같은 CSS 연출은 실시간이라 눌러서 바로 찍는다.
- **객관 검사**(`report.json`): 포커스 요소, 가로·세로 넘침, 44px 미만 조작 요소, 13px 미만 글자, 깨진 이미지, `overflow:hidden`에 일부 잘린 요소, 페이지 오류·콘솔 오류·실패한 요청. 전 장면 **페이지 오류·콘솔 오류·실패 요청 0건**이다.
- **장면 더하기**: `SCENES`에 `{ id, slug, title, sizes, save: { builder, args }, steps: [...] }` 한 줄을 더한다. 동작(`op`)은 `open·fill·click·tapCell·wait·run·runUntil·resume·scrollTop·scrollInto·shot`이다. 새 상태가 필요하면 `saves.ts`의 `BUILDERS`에 함수를 더한다. 맵 미리보기는 `save` 없이 `url: '/?previewMap=river_z'`(P3에서 개발 빌드 미리보기를 연 뒤)를 주면 된다. `save.args.grade`로 맵을 고르는 길은 4~6학년 공개 문제은행이 생기기 전에는 이어하기가 막힌다(`session.ts` `resumeBlocker`).
- 캡처 폴더(임시): `/private/tmp/claude-501/-Users-bodyking-Desktop-vibecoding/99a114b9-3f99-492f-86dd-684566151994/scratchpad/qa-p1/`. 위 명령으로 다시 만들 수 있다(약 90초).

## 3. 저사양 성능(§3.2)

**측정 방법**: 장면 7과 같은 방어(타워 10기)로 W18을 엔진으로 돌려 연출이 가장 많은 330틱(11초) 구간을 골라(`fx-window`: 적 20마리 안팎·비행 5·분열 3·장판·덫·굴림체·폭발) 그 시작에서 이어하고, 1440×900에서 실시간 10초 동안 `requestAnimationFrame` 간격을 쟀다. 평균 fps = 프레임 수/시간, 50ms 초과 = 간격이 50ms를 넘은 프레임 비율. 성문은 측정 중 지지 않게 늘렸다. 실제 GPU(Apple M6, Metal)로 그린다. **소프트웨어 GL(기본 헤드리스 셸)은 CPU 감속과 무관하게 1배속에서도 20fps대**(부하 구간, 아래 표 ⑤)라 성능 측정에 쓰지 않았다. "분위기 층 끔"은 개발 서버에서는 모듈을 대역으로 바꿔, 운영 빌드에서는 `AmbientLayer`를 빈 클래스로 빌드해 만들었다(소스 변경 없음).

**목표**: 4배 감속에서 평균 45fps 이상·50ms 초과 5% 이하, 6배 감속에서 평균 30fps 이상.

### 판정: 저사양 자동 단계는 **구현하지 않았다**

- 학생이 쓰는 **운영 빌드**는 4배·6배 모두 목표를 크게 넘고(59.8~60fps, 50ms 초과 0%) 16배 감속까지 58fps대라 여유가 크다. 개발 서버도 부하가 보통일 때 목표를 넘는다(6배 56fps). 따라서 §3.2의 "목표를 넘으면 구현하지 않는다"에 따라 자동 단계(나비·잔물결 → 구름 그림자 → 색조 즉시 전환)를 만들지 않았다.
- **분위기 층의 비용은 측정 오차 안**이다(켬/끔 차이: 개발 6배 0.3fps, 운영 0). 현재 분위기 층은 성능 문제의 원인이 아니다.
- **검증 대기**(PRD v0.5 기준표): 이 측정은 CPU 감속 모사이며 실기기 크롬북(GPU·메모리·열 제한)이 아니다. 실기기에서 미달하면 §3.2의 단계를 `AmbientLayer`(나비·잔물결·구름·색조)와 `bridge.reducedMotion` 경로에 붙이면 되고, 같은 장비로 `node tools/qa/perf.mjs --target prod`를 다시 돌려 확인한다.
